### EDA-P-08: Event delivery is reliable

#### Description

In distributed systems, reliable delivery means ensuring events are not lost even in the presence of failures. While exactly-once delivery is attractive in theory, it is rarely practical: crashes and restarts on the producer or consumer side make it extremely hard to guarantee that a message is delivered and processed exactly once without large complexity and performance costs.

For example:
*	A producer may crash after sending a message but before recording that it was sent. On restart, it may send the same message again.
*	A consumer may crash after processing a message but before recording that it was processed. On restart, it may process the same message again.

Because of these failure modes, most event-driven systems rely on an at-least-once delivery guarantee to ensure no events are lost. The tradeoff is duplicate deliveries - so consumers must be designed to tolerate duplicates (for example, by using event IDs and deduplication, recording processed offsets, or making operations idempotent).

The combination of at-least-once delivery guarantees plus idempotent consumers is the pragmatic, preferred approach: it is simpler, more robust, and more scalable than attempting to enforce system-wide exactly-once semantics.

#### Rationale

*   Prevent data loss: Events represent immutable business facts that carry critical state changes. Lost events lead to data inconsistency, incomplete business processes, and potential data loss across the distributed system. Reliable delivery ensures system integrity and maintains events as the authoritative source of truth.
*   Business continuity: Reliable delivery ensures business processes can continue even during system failures, preventing operational disruption and maintaining service availability for users.
*   Compliance and audit requirements: Many business domains require complete audit trails and regulatory compliance, making event loss unacceptable from a legal and governance perspective.

#### Implication

*	Consumer idempotency: Since distributed systems can only guarantee at-least-once delivery rather than exactly-once delivery, consumers must be designed to handle duplicate events. Event deduplication enables consumers to achieve idempotency by identifying and discarding events that have already been processed.
*	Configuration requirements: To implement at-least-once delivery, each component (producer, broker, and consumer) must configure specific system parameters. To minimize data loss risk, components should persist in-transit events using persistent queues and only remove them after receiving acknowledgment from the downstream component. Additionally, adopting synchronous send ensures that a producer only considers an event 'sent' once the broker has durably stored it. This approach, combined with client acknowledge mode and last participant support patterns, guarantees event durability throughout the delivery chain.
*	Monitoring and alerting: Reliable delivery requires comprehensive monitoring of delivery metrics, failed messages, and retry queues to detect and respond to reliability issues promptly.
*	Acknowledge messages properly The consumer must send acknowledgments back to the message broker/producer only after successfully processing the message. Acknowledging before processing risks message loss, while failing to acknowledge after successful processing causes unnecessary redelivery [Project Notifications 2022].
*	Strict sequencing: A single queue with a single consumer preserves message order, but only if no redeliveries occur. With durability mechanisms (persistent queues, synchronous send, and acknowledgments), no events are lost, but at-least-once delivery can trigger redeliveries, which may break strict sequencing even in a single consumer scenario. Combining both guarantees is possible but costly: to maintain both in-order delivery (FIFO) and at-least-once delivery, the system must process messages one at a time using stop-and-wait processing - sending each message and waiting for acknowledgment before proceeding to the next. This preserves order since redeliveries cannot overtake newer messages, but significantly reduces throughput and increases latency due to the elimination of parallelism. Once the system scales out to multiple consumers or multiple queues, strict sequencing can no longer be guaranteed, although durability (at-least-once delivery) is still ensured.
