### EDA-P-07: Asynchronous processing is the preferred interaction pattern

| Strategy | Asynchronous processing is the preferred interaction pattern. |

#### Description

While Event-driven architecture (EDA) supports both synchronous and asynchronous interactions, asynchronous processing remains the primary and preferred pattern. This preference reflects both the inherent nature of events and the architectural benefits that asynchronous communication provides.

An event represents an immutable fact - something that has already happened and cannot be altered. When an event such as 'OrderCreated' or 'MeterReadingUpdated' is published, it serves as a record of a completed action rather than a request for permission or validation. Since the event reflects a past occurrence, the producer has no requirement to wait for consumer functional acknowledgment or processing to complete. In contrast to a command and document message, an event carries no intention and has no recipient [EDA-P-03].

An event-driven system has producers, consumers, and an event broker. The event broker reliably transmits events from producers to consumers. Producers detect, gather, and send events without knowing who consumes them or how they are used. However, in the energy sector, this characteristic is less prominent, as energy producers typically have greater knowledge of their consumers. Consumers react to events as they receive them, either through self-contained actions or by coordinating multiple processes. 

The core reason EDA favors asynchrony is that the producer has no reason to block or await a reply: the event is a record of something that already happened, so the system can treat it as a one-way notification.

#### Rationale

*   Decoupling (loose coupling): In an event-driven architecture, producers and consumers work independently. A producer doesn't need to know which consumer will handle an event, or when they will do so. Events can be broadcast without knowing which consumers will subscribe to them or how they'll process them.
*   Publish-subscribe model: Events are facts, not requests. They're produced without intent or recipient, which makes them the perfect match for publish–subscribe, where messages are broadcast and consumers self-select whether they care.
*   Provides built-in resilience Event brokers can buffer and queue events when consumers are slow or unavailable. This prevents cascading failures and allows systems to handle load spikes gracefully without blocking producers.
*   Optimizes for scalability Asynchronous processing allows consumers to scale independently based on their processing capacity, while producers can emit events without being constrained by the slowest consumer in the system.
*   Best practice: Asynchronous communication is the established best practice for event-driven architecture. This approach aligns with the fundamental nature of events as immutable facts and delivers optimal architectural benefits. Following asynchronous-first design ensures event-driven systems deliver their intended architectural advantages while maintaining flexibility for exceptional cases where immediate consistency is truly required.
*   Increased responsiveness: Asynchronous communication dramatically improves system responsiveness by separating user acknowledgment from backend processing. Users receive immediate confirmation that their action was accepted, while complex operations execute independently in the background. This creates faster perceived performance - users no longer wait for slow downstream processes or system bottlenecks, resulting in systems that feel more responsive and reliable from the user's perspective. [Richards 2021].

#### Implication

*   Eventual consistency: Asynchronous event processing results in eventual rather than strong consistency. When an event is published, consumers handle it at their own pace, creating short periods where services have different views of state. For example, after an OrderPlaced event, the order service may show the new order while the inventory service updates later. This trade-off is central to asynchronous EDA: it enables scalability and resilience but requires systems to tolerate temporary inconsistencies until all consumers have processed the events.
*   Ordering and delivery considerations: Asynchronous processing introduces complexities around message ordering, duplicate handling, and delivery guarantees that are worth acknowledging.
*   Error handling complexity: While async provides resilience benefits, it also makes error handling and debugging more complex since immediate feedback isn't available.
*   Deduplication and idempotency (at-least-once delivery): Events may be delivered multiple times due to retries or failures. Consumers must handle potential duplicates by implementing idempotent processing to ensure correct outcomes.
