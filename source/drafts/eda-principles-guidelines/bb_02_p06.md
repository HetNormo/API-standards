### EDA-P-06: An event design-first approach is followed

| Strategy | An event design-first approach is followed. |

#### Description

_Event design-first_ means designing the structure, schema, and contracts of events before implementing the application or system logic, similar to the design-first approach in API development. This approach ensures that events are well designed, documented, and understood across teams, reducing integration issues and semantic coupling later in development. Design-first stresses the methodology of designing before coding.

The event design-first approach treats events as first-class citizens in the development of event-driven systems. By prioritizing events upfront, the system’s architecture becomes inherently aligned with business processes and their language, ensuring that events capture meaningful state changes accurately and consistently.

This approach also enables loose coupling, as event producers publish events without knowledge of consumers, allowing the system to evolve more flexibly. It  leads to more intentional and thoughtful schema definition, reducing semantic coupling and improving maintainability and scalability.

#### Rationale

*   Reduced semantic coupling: In event-driven systems, one of the most significant remaining sources of coupling is semantic coupling - the structure and meaning encoded in the event schema. To address this, it is essential to practice an event-first design approach, being deliberate and thoughtful in how event schemas are defined and refined.
*   Best practice: Design first approach is an industry wide adopted best practice.
*   Aligns with business language and processes: The approach encourages events to capture meaningful business processes and state changes in the domain language by involving domain experts, ensuring technical implementation reflects business realities. The event-first mindset usually involves collaborative techniques like _Event Storming_ to bring stakeholders together and clarify system behaviors early.
*   Peer and consumer review: By defining contracts separately from code, we enable early peer and consumer review, fostering a development discipline that prioritizes comprehensive understanding of the domain and required functionality. This approach ensures that service interface design is deliberate and aligned with business needs before implementation begins.

#### Implication

*   Code-first approach is not applied: In the design-first approach, the API design is defined upfront - before any implementation begins. In contrast, the code-first approach starts with building functionality, and the API design emerges as development progresses. Design-first avoids implementation-driven APIs, streamlines development, improves documentation quality, and is preferred over code-first.
*   Design deliverables: Event design has to be documented as a design deliverable. The preferred deliverable is the contract: an approved asynchronous API design, represented by its description or schema, which serves as the contract between stakeholders, implementers, and consumers. The description or schema is the single source of truth, not the API implementation. For event/message schemas in event-driven APIs, the standard contract format is _AsyncAPI_ for documenting event-driven architectures.
*   Collaborative discovery and design: This principle requires an _event-first mindset_ grounded in collaborative discovery. Events must be _discovered_ - not invented in isolation - by domain experts, product owners, engineers and architects working together. Collaborative discovery sessions (for example, _Event Storming_ or _Event Modeling_) come first: they surface the real domain events, ubiquitous language, business rules, and pain points that should drive event design. These discovered events then form the source for event schemas, contracts and downstream designs.
