### EDA-P-04: Events are either of type notification or state transfer

| Strategy | Events are either of type notification or state transfer. |

#### Description

In event-driven systems, every event should be classified as one of two types:

*	_Notification event_: A lightweight event primarily intended to inform interested systems that a significant occurrence has taken place. These events typically include only metadata, enabling consumers to optionally retrieve additional details from the source system. This pattern promotes loose coupling but may increase network chattiness. This type is also referred to as a 'thin' event.

*	_Event-carried state transfer_ (state transfer event): An event containing sufficient data to allow consumers to fully comprehend and act upon the change without needing to query the source system. Such events encapsulate the relevant business state as a complete snapshot, empowering consumers to process, store, or synchronize information independently. The state transfer event includes the full representation of the resource, similar to a REST API response. This pattern reduces runtime dependencies but increases event size and coupling to data schemas. This type is also known as a 'fat' event.

Avoid hybrid events: Events should not be ‘medium-sized’ with some but not all necessary data. Other event patterns exist (_delta events_, _mutation events_, _domain events_, _summary events_) but can typically be mapped to these two fundamental approaches.

#### Rationale

*	<u>Simplification</u>: Encourages clear contracts and simplifies event classification by reducing decision complexity to a binary choice.
*	<u>Separation of concerns</u>: Differentiating between lightweight notifications and state transfer events clarifies the architectural tradeoff: notifications optimize for _single source of truth and minimal payloads_, while state transfer events optimize for _autonomy and independence from source systems_.
*	<u>Explicit role of metadata</u>: By defining that notification events carry only metadata, the design enforces a clear contract where metadata signals ‘what happened' while the corresponding API provides the 'details'. This separation enhances maintainability and consistency across the event landscape.
*	<u>Alignment with industry practices</u>: This classification is widely recognized in event-driven architecture literature and industry standards, ensuring interoperability and a shared vocabulary across teams and systems.

#### Implication

*   <u>Exclusivity of event types</u>: Other event variations (e.g., _delta_, _mutation_, or _summary_ events) should be modeled as specializations of either notification or state transfer. This enforces consistency and prevents the emergence of 'hybrid' or ambiguous event definitions. Decision: clear architecture principles must come to decide between notification and state transfer event types.
*	<u>Architectural decision point</u>: Teams must explicitly decide whether to publish an event as a notification or as a state transfer. This decision should be guided by architectural drivers such as _decoupling needs_, _consumer autonomy_, _system load_, and _data governance_ requirements.
*	<u>API dependencies</u>: Notification events require a stable and accessible API for consumers to retrieve additional details (runtime coupling). In contrast, state transfer events reduce runtime dependencies by embedding the full resource representation (schema coupling). If both a state transfer event and an API exist for the same resource, the representation in the event must remain consistent with the structure returned by the REST to avoid schema drift.
*	<u>Organizational impact</u>: Adopting this principle requires governance to ensure consistent classification across teams, proper schema evolution practices, and documentation of corresponding APIs when notifications are used.
*	<u>Event sourcing trade-off</u>: Event-carried state transfer provides immediate access to complete entity state but creates tension with event sourcing patterns, which rely on minimal delta events for efficient state reconstruction. The full state embedded in events generates larger streams with redundant data and complicates schema evolution, making delta events a better fit for event sourcing implementations despite requiring consumers to maintain more complex state rebuilding logic.
