### EDA-P-11: Event-driven systems are evolvable

| Strategy | Event-driven systems are evolvable. |

#### Description

Event-driven systems are highly evolvable because producers and consumers operate independently, without direct knowledge of each other. This loose coupling makes it easy to add new services: they can simply subscribe to existing events or publish new ones, without requiring changes to the existing components.
This loose coupling means changes in one part don't force updates everywhere else, making the system easier to extend.

However, this independence introduces a challenge, particularly for event-carried state transfer patterns where events contain rich domain data rather than simple notifications with only metadata. Since producers don’t know which consumers rely on their events, a schema change can unintentionally break downstream services. With no visibility into these dependencies, producers face significant risk when modifying event structures - unless proper versioning and backward compatibility strategies are in place.

Evolvability guidelines establish rules for backward compatibility, versioning strategies, and deprecation processes that protect consumers from unexpected failures.

#### Rationale

*	<u>Adapt to change</u>: Business environments, regulations, and customer expectations evolve constantly; systems must be able to keep pace without costly rewrites.
*	<u>Preserve independence</u>: Loose coupling between producers and consumers enables services to evolve independently, reducing the risk of brittle dependencies.
*	<u>Extensibility</u>: New services or capabilities can be added incrementally by subscribing to existing events, improving time-to-market and enabling experimentation.
*	<u>Maintain stability</u>: Versioning and compatibility strategies protect downstream consumers from unexpected failures during schema evolution.

#### Implication

*	<u>Metadata pattern</u>: Event schemas create the strongest coupling in event-driven architecture. To preserve evolvability, structure events with separate metadata and data sections, where the metadata contains version information for schema evolution.
*	<u>Schema versioning</u>: Schema versioning is critical for evolvable event-driven systems. Versioning enables safe evolution by allowing producers to introduce new formats while consumers process older versions at their own pace. This prevents cascading failures and supports gradual migration across services.
*	<u>Governance process</u>: Establishing clear governance processes is essential for managing schema evolution across teams and services. This includes defining approval workflows for schema changes, setting deprecation timelines for old versions, and maintaining a central schema registry. Governance ensures that schema modifications follow consistent patterns, backward compatibility requirements are enforced, and all stakeholders are notified of upcoming changes through proper communication channels.
