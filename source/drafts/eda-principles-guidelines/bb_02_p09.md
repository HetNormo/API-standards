### EDA-P-09: Failure is controllable through robust error handling

#### Description

Event processing can fail in numerous scenarios across the distributed landscape of modern systems. These scenarios should be handled gracefully - automatically where possible, and with human intervention when needed. To make failure modes manageable and observable, classify message-processing failures into two high-level categories that form the foundation of robust error handling strategies:

*	Transient failures: temporary, retryable problems that are likely to resolve themselves given time or changed system conditions, like: network connectivity, downstream service overload or timeouts, CPU load, and service crashes
*	Persistent failures: permanent or non-retryable problems where additional automatic retries will not resolve the underlying issue and may cause system degradation like: software bugs, invalid or corrupted payloads (poison messages), incompatible or missing schema versions, infrastructure and configuration issues or missing required business data

Distinguishing transient (temporary, retryable) from persistent (permanent, non-retryable) failures is central to EDA error-handling strategies: it determines whether automated retries are appropriate, when to invoke circuit breakers, when to involve humans, and when to preserve the message for later investigation and replay.

#### Rationale

*	<u>Business continuity</u>: Mission-critical systems must continue processing viable events while quarantining problematic ones, maintaining core operations during infrastructure problems, and providing operators with visibility and control over failure propagation across distributed system topology.
*	Temporal decoupling makes error handling complex. Unlike synchronous calls where failure handling is immediate, event processing failures can occur hours or days after the triggering event was published. This requires sophisticated message preservation, failure classification, and replay mechanisms that don't exist in request-response architectures.
*	<u>Failure landscape</u>: In synchronous architectures, failures are immediate and local - easily handled by the calling code. EDA distributes processing across multiple services, networks, and time boundaries, where failures can manifest far from their root cause and persist across system boundaries.

#### Implication

*	<u>Transient failures</u>: use bounded retries with exponential backoff and randomization, respect a retry budget, combine with circuit breakers and bulkheads to avoid cascading load. Design consumers to be idempotent so retries are safe. If retries are exhausted, escalate the message to the persistent-failure flow (DLQ/quarantine) rather than retrying forever.
*	<u>Persistent failures</u>: immediately or after bounded retries route the message to a dead-letter queue (DLQ) or quarantine with full diagnostic context, raise alerts for human triage, then fix root cause and provide a safe replay path from DLQ. Reduce occurrences by using schema registries, contract tests, and producer validation.
*	<u>Observability</u>: Implement distinct metrics for transient vs. persistent failures, track retry success rates, monitor DLQ depth, and alert on classification accuracy to enable continuous improvement of error handling strategies.
